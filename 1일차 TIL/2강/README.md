## 1. 사용자 요청 단계

웹 서비스의 시작은 사용자가 브라우저나 앱에서 특정 행동을 하는 것이다.

사용자가 URL을 입력하거나 버튼, 링크 등을 클릭하면 브라우저는 해당 요청을 처리하기 위한 과정을 시작한다.

### 요청이 전달되는 과정

1. 사용자가 URL을 입력하거나 버튼을 클릭한다.
2. 브라우저가 DNS 서버에 요청해 도메인에 해당하는 IP 주소를 조회한다.
3. 브라우저가 해당 서버로 HTTP 또는 HTTPS 요청을 전송한다.

예를 들어 사용자가 다음 주소에 접속한다고 가정할 수 있다.

```text
https://naver.com/login
```

여기서 브라우저는 `naver.com`이라는 주소만으로 서버와 바로 통신하는 것이 아니라, DNS를 통해 실제 서버의 IP 주소를 확인한 뒤 요청을 전달한다.

또한 HTTPS는 HTTP에 보안이 추가된 방식이라고 이해할 수 있다.

---

## 2. Web Server와 WAS

서버라고 해서 모두 같은 역할을 수행하는 것은 아니다.

웹 환경에서는 대표적으로 **Web Server**와 **Web Application Server(WAS)**로 구분할 수 있다.

### Web Server

Web Server는 주로 **정적 리소스**를 처리한다.

정적 리소스란 요청할 때마다 내용이 변경되는 것이 아니라 미리 만들어져 있는 파일을 의미한다.

대표적인 정적 리소스는 다음과 같다.

- HTML
- CSS
- JavaScript
- 이미지

대표적인 Web Server로는 다음이 있다.

- Nginx
- Apache

---

### WAS

WAS(Web Application Server)는 사용자의 요청에 따라 결과가 달라질 수 있는 **동적인 처리를 담당하는 서버**이다.

사용자의 로그인 요청이나 게시물 작성처럼 서버 내부에서 특정 로직을 실행해야 하는 요청들이 이에 해당한다.

이번 강의에서는 WAS가 Web Server의 기능을 포함할 수 있는 구조로 설명되었다.

---

## 3. 서버의 요청 처리 과정

클라이언트의 요청이 서버에 도착하면 서버 내부에서도 여러 단계를 거쳐 처리된다.

전체적인 흐름은 다음과 같이 이해할 수 있다.

**Web Server → Application Server → Database**

### ① Web Server

Nginx나 Apache와 같은 Web Server가 클라이언트의 요청을 먼저 받는다.

정적 리소스에 대한 요청이라면 직접 처리할 수 있으며, 추가적인 로직이 필요한 요청은 Application Server로 전달한다.

---

### ② Application Server

Spring Boot와 같은 Application Server에서는 전달받은 요청을 실제 비즈니스 로직에 따라 처리한다.

강의에서는 다음과 같은 흐름으로 요청을 처리한다고 설명했다.

**Controller → Service → Repository**

- **Controller**: 사용자의 요청을 전달받는 역할
- **Service**: 실제 서비스의 로직을 처리
- **Repository**: 데이터베이스에 접근

이 과정을 통해 서버 내부의 역할을 분리하여 요청을 처리할 수 있다.

---

### ③ Database

Database에서는 서비스에 필요한 데이터를 처리한다.

대표적인 동작은 다음과 같다.

- 저장(Create)
- 조회(Read)
- 수정(Update)
- 삭제(Delete)

애플리케이션 서버가 DB에 데이터를 요청하면 데이터베이스가 해당 요청을 처리한 뒤 결과를 다시 반환한다.

---

## 4. ORM

ORM(Object Relational Mapping)은 **객체와 관계형 데이터베이스를 연결해주는 기술**이다.

일반적으로 프로그램에서는 객체를 사용하지만 데이터베이스에서는 테이블 형태로 데이터를 관리한다.

ORM은 이러한 두 구조를 서로 연결해준다.

```text
DB Table ↔ Class

Column ↔ Field
```

ORM을 활용하면 개발자가 모든 SQL을 직접 작성하지 않고도 객체 중심의 코드로 데이터베이스에 접근할 수 있다.

---

## 5. JPA와 MyBatis

강의에서는 데이터베이스 접근 방식과 관련하여 JPA와 MyBatis를 비교했다.

### JPA

JPA(Java Persistence API)는 Java에서 사용하는 표준 ORM 인터페이스이다.

대표적인 구현체로 Hibernate가 있다.

JPA를 사용하면 SQL을 직접 작성하는 비중을 줄이고 객체 중심으로 데이터를 처리할 수 있다.

```java
userRepository.findById(1L);
```

개발자가 직접 SQL을 작성하기보다는 객체와 메서드를 이용해 데이터를 조회하는 방식이다.

### MyBatis

MyBatis는 ORM보다는 **SQL Mapper**에 가까운 방식이다.

SQL을 직접 작성하지만 SQL의 결과를 Java 객체와 연결해준다.

```sql
SELECT *
FROM users
WHERE id = #{id}
```

SQL을 직접 제어할 수 있기 때문에 세부적인 쿼리 작성이나 최적화가 필요한 경우 활용할 수 있다.

---

## 6. JPA와 MyBatis의 차이

두 기술의 가장 큰 차이는 SQL을 다루는 방식에 있다.

| 구분 | JPA | MyBatis |
| --- | --- | --- |
| 중심 | 객체 중심 | SQL 중심 |
| SQL 작성 | 자동 생성 중심 | 직접 작성 |
| 추상화 | 높음 | 비교적 낮음 |
| 특징 | 객체지향적인 데이터 처리 | SQL을 세부적으로 제어 가능 |

정리하면,

**JPA는 객체 중심으로 DB를 다루기 위한 방법이고, MyBatis는 SQL을 직접 작성하면서 객체와 연결하는 방법이다.**

---

## 7. 클라이언트 처리 과정

서버가 요청을 처리한 후에는 처리 결과를 클라이언트에게 다시 전달한다.

브라우저나 SPA Framework는 서버가 전달한 JSON이나 HTML 등의 응답을 받는다.

그 이후 화면을 만들어 사용자에게 보여준다.

### HTML

HTML을 기반으로 화면의 구조인 DOM을 생성한다.

### CSS

생성된 화면 구조에 디자인과 스타일을 적용한다.

### JavaScript

사용자의 행동에 따른 동적인 처리를 담당하며 서버 API와 통신하는 역할도 수행한다.

최종적으로 브라우저가 모든 내용을 화면에 표시하면 사용자가 결과를 확인할 수 있다.

사용자가 다시 버튼을 클릭하거나 새로운 기능을 실행하면 다시 서버에 API 요청을 보내며 같은 과정이 반복된다.

## 8. 웹 서비스의 전체 흐름

이번 강의를 통해 웹 서비스의 처리 과정을 조금 더 구체적으로 정리하면 다음과 같다.

```text
사용자
  ↓
브라우저
  ↓
DNS 조회
  ↓
HTTP / HTTPS Request
  ↓
Web Server
  ↓
Application Server
  ↓
Database
  ↓
처리 결과 반환
  ↓
브라우저
  ↓
HTML / CSS / JavaScript 렌더링
  ↓
사용자 화면 표시
```

즉, 사용자가 웹 브라우저에서 특정 행동을 했을 때 단순히 서버 하나가 처리하는 것이 아니라 여러 영역이 각각의 역할을 수행하면서 하나의 요청을 처리한다.

## 💡 새롭게 알게 된 점

1강에서는 웹 서비스가 **Client → Server → Database** 구조로 동작한다는 전체적인 흐름을 배웠다면, 이번 강의에서는 그 과정에서 실제로 어떤 단계들이 존재하는지를 조금 더 구체적으로 이해할 수 있었다.

특히 사용자가 URL을 입력하면 바로 서버로 접근하는 것이 아니라 **DNS를 통해 도메인에 해당하는 IP 주소를 먼저 찾은 후 서버에 요청을 전달한다는 과정**을 알게 되었다.

또한 서버 역시 하나의 구성 요소가 아니라 **Web Server와 Application Server가 서로 다른 역할을 담당할 수 있다는 점**을 이해했다.

데이터베이스 접근에서도 개발자가 항상 직접 SQL을 작성하는 것이 아니라 ORM을 활용해 객체 중심으로 데이터를 처리할 수 있으며, JPA와 MyBatis처럼 데이터베이스에 접근하는 방식에도 차이가 있다는 점이 인상적이었다.
